Noria: caching that invalidates itself

July 25, 2026 · 3 min read

Why I keep coming back to this repo

One of my favorite GitHub projects is mit-pdos/noria, a research project out of MIT PDOS (Jon Gjengset's PhD work, later commercialized as ReadySet). It attacks a problem every backend engineer has quietly suffered through: cache invalidation. Not "how do I cache this query" — that part is easy — but "how do I know when to throw the cache away," which is the actual hard half of the famous two-hard-things joke.

The idea

Most systems bolt memcached or Redis in front of Postgres and then hand-write invalidation logic scattered across the codebase: update this row, remember to bust that key. It works until it doesn't. I remember a famous saying by 2 hardest problem in computer science: cache invalidation and naming things. Noria is a research project that tries to solve this problem by treating your SQL queries as a dataflow graph, where base tables are inputs and every cached query is a materialized view sitting downstream in the graph, kept fresh by streaming deltas through the operators whenever the base data changes. Noria flips this around. Instead of caching query results as a side effect, it treats your SQL queries as a dataflow graph. Base tables are inputs, and every cached query is a materialized view sitting downstream in the graph, kept fresh by streaming deltas through the operators — joins, aggregations, filters — whenever the base data changes. There is no invalidation step because there's nothing to invalidate; the view is always derived, incrementally, from the write path itself.

What I actually find clever

The "partially-stateful" part is the neat trick. A naive dataflow system would materialize every intermediate operator, which gets expensive fast. Noria instead evicts state it doesn't need and lazily rematerializes it on a cache miss by replaying the necessary slice of upstream data — so it behaves like an LRU cache, except the "cache miss" path is a real, correct dataflow computation instead of a fallback query to the source of truth. It's the same instinct behind incremental view maintenance in systems like Materialize or differential dataflow, but Noria's angle — plug in as a MySQL-compatible layer, keep your existing queries — makes the idea land as something you could plausibly retrofit onto a real app rather than a green-field rewrite.

Where it left me

The original repo is mostly dormant now (the commercial fork, ReadySet, is where active development moved), but the codebase and the accompanying paper are still one of the clearest treatments I've read of "what if the cache and the database were the same system." If you've ever hand-rolled invalidation logic and hated it, it's worth an afternoon.
