Building an ACID LSM-Tree Storage Engine in Go, From Scratch

May 24, 2026 · 12 min read

I'm writing a key-value storage engine in Go. No libraries for the interesting parts — the skiplist, the SSTable format, the bloom filter, the compaction scheduler, and the MVCC layer are all built by hand. The goal is a small embeddable engine with real ACID transactions and one writer node with many read-only replicas.

This post is the design, written down before most of the code exists. If you've read the LevelDB source and always wanted to know why it's shaped that way, this is that walkthrough.

Why LSM instead of a B-tree

A B-tree updates data in place. Every write touches a random page on disk. That's fine on a spinning disk with a big cache, and terrible when your write rate is high.

An LSM-tree (log-structured merge tree, O'Neil et al., 1996) makes a different trade:

  • Writes go to an append-only log and an in-memory sorted table. Both are sequential. Fast.
  • When memory fills, the table is dumped to disk as an immutable file (an SSTable).
  • A background process (compaction) merges those files over time to keep read costs bounded.
