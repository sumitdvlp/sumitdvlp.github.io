memcache-go: Building Memcached From Scratch in Go

September 15, 2026 · 8 min read

I was practicing coding and writing LRU cache, and then i thought the current thread safe implementation is sufficient for correctness under concurrent access but not good enough for write heavy contention. The biggest win will be sharding but the tradeoff: eviction becomes approximate. So added a janitor for cleanups.

memcache-go is a distributed Memcached clone I wrote in Go: a single-node, in-memory, LRU-evicting, TTL-aware key/value store that speaks the real Memcache text protocol, plus a consistent-hashing client that routes keys across a multi-node cluster. No caching library underneath. Memcached is one of those systems everyone has used and almost no one has re-derived, and the interesting parts turned out to be smaller and sharper than I expected.

The shape of the project

Three layers, cleanly separated:

  • memcache/ — the single-node engine: an LRU+TTL Store, a text-protocol connection handler, the TCP server, and stats counters.
  • cluster/ — a hash function and a consistent-hash Ring that maps keys to physical nodes.
  • client/ — a pooled cluster client that wraps the ring: callers just call Get/Set and never think about which node owns which key.

A node knows nothing about the cluster. All the routing intelligence lives in the client, which is the same design real Memcached uses — the servers are dumb, stateless, and don't talk to each other at all.

The store: O(1) LRU without a library

The core data structure is the textbook LRU cache: a doubly-linked list ordered by recency (container/list) plus a map[string]*list.Element for O(1) lookup. Every Get moves its element to the front; eviction always pops from the back.

func (s *Store) Get(key string) ([]byte, uint32, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()

    el, ok := s.items[key]
    if !ok {
        s.getMisses++
        return nil, 0, false
    }
    it := el.Value.(*item)
    if it.isExpired(time.Now()) {
        s.removeElement(el)
        s.expired++
        s.getMisses++
        return nil, 0, false
    }
    s.ll.MoveToFront(el)
    s.getHits++
    out := make([]byte, len(it.value))
    copy(out, it.value)
    return out, it.flags, true
}

Two things worth calling out. First, eviction is size-bounded, not count-bounded — the store tracks approximate memory usage (key length + value length per entry) against a configured maxBytes, and evictIfNeeded() pops from the tail of the list until it fits. That mirrors real Memcached's -m flag far better than a "max N keys" limit would, since key/value sizes in practice are wildly uneven.

Second, both Set and Get copy the byte slice in and out. It's a small allocation cost per operation, but it means the store never hands out a slice a caller could mutate underneath a concurrent reader — no aliasing bugs, no need to document "don't touch this after you get it back."

TTL is lazy plus a sweep: expiry is checked on read (a Get against a stale key evicts it on the spot and counts as a miss), and a background janitor goroutine walks the list from the back every cleanupInterval and reaps anything expired, so keys that are never read again don't sit around forever burning memory. Since the list is ordered by recency and not by expiry, the janitor's sweep is a full O(n) scan rather than a heap-based "next expiring key" pop — a deliberate simplicity-over-throughput tradeoff, fine at the scale this is meant for.

Speaking the actual protocol

The point of building this wasn't just "a cache with a Go API" — it needed to be a drop-in Memcached speaker, testable with nc or telnet and usable by any existing Memcache client library. The handler reads line-by-line off a buffered reader, splits on whitespace to get the command and its arguments, and dispatches:

  • get / gets — fetch one or more keys
  • set — store a value; reads the command line (key, flags, exptime, byte count), then a separate io.ReadFull() for the exact-length binary payload that follows
  • delete, flush_all, stats, version, quit

The fiddly bit is exptime: the Memcache protocol overloads one field to mean two different things — a relative number of seconds if it's ≤ 30 days, or an absolute Unix timestamp otherwise. expTimeToTTL() handles that branch and converts either form into a plain time.Duration, so the store itself never has to know the protocol existed. Values are capped at 1 MiB, matching Memcached's own default item-size ceiling.

Consistent hashing: the part that makes it a cluster

A single node is just a cache. What turns this into memcache-go rather than memcache-go-node is the cluster.Ring: a thread-safe consistent-hash ring where each physical node is placed at 160 points ("virtual nodes") around the hash space to keep the key distribution balanced even with a small node count.

Operation How Cost
Get(key) hash the key, binary-search the sorted virtual-node slice for the first hash ≥ h, wrap around if none found O(log n)
GetN(key, n) walk clockwise from that point collecting distinct physical nodes, for replication O(n)
Add / Remove insert/delete the 160 virtual-node hashes for that physical node, rebuild the sorted slice O(n log n)

This is the whole reason consistent hashing exists instead of plain hash(key) % N: adding or removing a node only reshuffles the keys that landed on that node's ~160 arcs, not the entire keyspace. With modular hashing, changing N by one invalidates almost every key's mapping at once — a cache-wide cold start at exactly the moment (a node joining or dying) when you can least afford one.

Client-side routing, server-side ignorance

The design leans hard on one decision: nodes are completely stateless and unaware of each other. There's no gossip, no coordinator, no rebalancing protocol — the client package holds the ring and a connection pool per node, and simply looks up the right node before every request. This is exactly how production Memcached clusters have always worked (Facebook's mcrouter is the industrial-strength version of the same idea), and it buys real simplicity: no split-brain, no consensus, no server-side code that needs to know about cluster membership at all. The cost is the one you'd expect — the client owns correctness of the topology, and a node that goes down doesn't fail over, it just becomes unreachable until the client's view of the ring is updated. That's an acceptable trade for a cache: it's explicitly not the system of record, so losing an unreachable node's keys is a cold cache, not data loss.

Running it

A single node with a 64 MiB cap:

go run ./cmd/server --port 11211 --max-memory 64mb

# then, from anywhere that speaks the protocol:
printf 'set foo 0 0 3\r\nbar\r\n' | nc localhost 11211
printf 'get foo\r\n' | nc localhost 11211

And a 3-node cluster via the included Docker Compose file, driven from Go through the cluster client:

c := client.New([]string{"node1:11211", "node2:11211", "node3:11211"})
c.Set("session:42", []byte("payload"), time.Minute)
val, ok := c.Get("session:42")

What's deliberately missing

No persistence — restart a node and its data is gone, same as real Memcached. No server-side replication or automatic failover; GetN exists in the ring so a client could write to N nodes for redundancy, but that policy decision is left to the caller rather than baked into the server. No dynamic cluster membership discovery — the client is handed a static node list. All three are the right scope cuts for what this project is: a faithful, from-scratch reimplementation of the parts of Memcached that are actually instructive to build, not a from-scratch reimplementation of everything ops tooling has grown around it over twenty years.

Code's at github.com/sumitdvlp/memcache-go.
