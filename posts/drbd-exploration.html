My journey of exploring DRBD at Azure

June 20, 2026 · 20 min read

Some background

I was part of Azure's open source database migration team, where we shepherded customer databases to the cloud one careful byte at a time. Migrating databases is like moving a sleeping toddler and a vase at the same time — one wrong move and someone cries or break(trust/revenue). Data cannot be corrupted or lost during migration. What I loved about the job was getting deep into the internals of Postgres and MySQL. Most of our solutions leaned on native DB technologies like WAL log replication, dump/restore, and native replication — basically the database equivalent of duct tape and a prayer. Thanks for reading this far; I just wanted to set the scene before I hit the point. One more pre-context note: I was exploring CRDT systems for some other project when I ran into DRBD, and suddenly things got even more delightfully nerdy. For migration, we were using native replication and dump/restore, but I was curious about other replication technologies that could be used for database migration. DRBD is a block-level replication technology that can be used to replicate data between two servers. It is often used in high-availability clusters, but it can also be used for database migration. Here is my full post on DRBD Explained.

The Plan

Our migration used to stuggle a lot during transient error during dump/restore and many times complete failure during causing restart the whole process again, this was very painful/frustrating for customers. And most of our oncall tickets were related to these issues. We wanted to explore DRBD as a potential replication technology for database migration, and see if it could help us avoid these issues. The two factors that we wanted to explore were:

  • How does DRBD perform under network partitioning?
  • How does DRBD perform under different hardware configurations?
2 metrics we wanted to measure were:
  • Latency of writes on the primary node during network partitioning.
  • How quickly the partitioned node can catch up with writes after the network partition.
And ofcourse if this setup brings any cost/performance tradeoffs for database migration.

The Setup

I setup cluster of 3 Azure Linux VMs with one primary and two secondary nodes. Similar to this setup guide. Primary node is responsible for writing data and secondary nodes are responsible for reading data.

  • 3 Small VM with HDD
  • 3 Small VM with SSD
  • 3 Medium VM with SSD
  • 3 Medium VM with SSD and high bandwidth network.
And ran gaming workload with small updates similar to https://github.com/baotiao/game-sysbench
  • 1. Force network partitioning by restarting one/all of the secondary nodes.
  • 2. Measure latency of writes on the primary node.

Results

CPU/VM size Disk type Workload type Performance
3 Small HDD Small Network partitioning increased latency
3 Small SSD Small Network partitioning increased latency
3 Medium SSD Medium Network partitioning increased latency
3 Large High Bandwidth SSD Medium Nodes were able to catchup quickly.
3 Large VMs high-bandwidth network SSD High Network partitioning increased latency
3 Medium VMs and high-bandwidth network SSD High Network partitioning increased latency, and the partitioned node was unable to catch up with writes

Conclusion

We should discuss tradeoffs instead of making a conclusion. The tech works in theory but there is a cost (literally). Large VMs with high-bandwidth network are expensive and not all customers can afford them. And they too only able to work on medium workloads. This was a test setup and we did not explore all the possible configurations. Because earlier result were not very encouraging. Hence question of relaiblity was not answered as well. I think DRDB is a good tech for file replication if you want build a system like dropbox or google drive. But for database a different layer of abstraction is needed. I also noticed another use case is HA for database. After reading this blog. But they didn't considered network partitioning and how it can affect TPS and latency.
